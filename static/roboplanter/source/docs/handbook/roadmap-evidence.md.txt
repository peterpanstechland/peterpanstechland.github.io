# 工位搭子 · 证据、验收与扩展路线

更新基线：2026-10-25。本文区分仓库已经实现、已有验证、尚未验证与未来规划。它是参赛材料和对外文案的事实登记表，不能替代原始日志；“已实现”不等于“接线即用”，“已上传”不等于“已发布”。

## 1. 当前可以怎样介绍

> RoboPlanter 是以工位绿植为起点的 YOYO 硬件交互原型。Indicator 实体屏幕已运行植物养成与本地专注功能；XIAO 固件实现了传感器读取和受限设备动作。YOYO 独立 Skill 已上传，手机 BLE 与真实外设的完整链路仍需实机验收。团队正在把这一套接入方法整理为可供用户硬件复用的能力模型与教程。

2026-10-25 已在控制台只读核对现存 0.2.0 技能文件、基本信息及 `hardware_ready:false`，详见 [平台教程](honor-platform.md)。仓库另有 2026-10-24 历史草稿记录，原始账号截图不随公开包分发。导入草稿、提交审核、已发布、手机真机闭环分别记录，不把这些状态混用。

## 3. 验证等级与展示标签

给展项使用短标签而不是混成“演示成功”：

- **方案**：设计、文档或未运行代码，注明规划。
- **主机测试**：模拟对象/本机编译/测试通过；记录命令、环境和结果。
- **原生预览**：运行生产绘图代码生成图像，但没有 LCD 时序、触摸或网络硬件。
- **实机单模块**：指定板卡和外设上验证一项功能；记录接线、固件哈希与观察。
- **端到端实机**：同一次用户意图，从 YOYO 手机请求到指定设备回包和现场结果，保留可关联记录。
- **持续场景试验**：在明确时间、样本、环境和维护条件下持续使用；不能从一次展台演示推定。

等级不是自动继承关系。主机测试越多不等于无线、电源、触摸或泵得到验证；端到端一次成功也不等于长期无人值守安全。

## 4. 首个完整闭环的验收卡

执行步骤见 [硬件首次接入](hardware-quickstart.md)、[荣耀平台教程](honor-platform.md)、[BLE 联调](ble-integration.md)；遇到异常先看 [排错](troubleshooting.md)。

每次验收卡记录：日期、操作者、硬件型号/修订、手机型号/系统、Skill 包版本与哈希、固件提交与镜像哈希、供电与驱动、已开启能力、测试步骤、请求 ID、设备启动时间、响应、现场观察、结果及附件路径。共享版本删去凭证、手机通知和个人信息。

按以下顺序推进，上一项不通过就修正后重测：

1. **默认禁用启动。** XIAO 刷入默认配置，只验证启动、HTTP/BLE 与禁用状态；泵/灯/打印不因启动或连接自动运行。
2. **只读链路。** 确认具体传感器及电平后，观察原始值随现场条件变化；未标定保持百分比未知。手机正确处理有效、无效、旧读数。
3. **驱动独立验证。** 先不接负载确认输出极性与复位关闭；再在可断电台架测试泵限时与停止，保留测量而非只听电机声音。
4. **手机 BLE 边界。** 确认通知订阅、长写/MTU、凭证注入、断线重连，禁止把令牌放在 Skill 提示词、截图或公开视频里。
5. **同一动作闭环。** 一次明确的短时浇水意图，关联请求 ID、受理、结束及现场结果。软件结束不宣称已达到目标含水量。
6. **故障复测。** 发送后断线、接收超时、旧读数、重复 ID、重启后找不到记录、外设未启用。结果未知时不重发，停止路径优先。
7. **用户任务。** 请未参与开发的人指出虚拟浇水与真实泵的差别，完成一次读取、一次取消、一次确认、一次结果未知恢复。

演示时先复核供电与设备状态；展台使用短脉冲和接水容器。必要的电气保护不能被软件计时替代。具体接线约束以硬件教程为准。

## 5. 评测指标：先定义，再采集

以下是内部验收目标，不是荣耀或任何赛事的官方评分。当前没有测量结果的项应保持空白，不能用目标值填“实际值”。

| 维度 | 测量定义 | 建议首轮目标 | 证据形式 |
| --- | --- | --- | --- |
| 虚实理解 | 未参与开发的参与者正确指出游戏浇水不驱动真实泵 | 8/8；出现误解先改设计再测 | 匿名任务记录与版本 |
| 结果理解 | 正确解释受理、完成、未知，知道未知不自动重试 | 8/8 | 三张状态卡的复述记录 |
| 首次读取 | 从准备齐全开始，到首次有效读取；单列失败与求助 | 先采基线，不虚设零成本门槛 | 屏幕录像与阶段时间 |
| 动作可关联 | 每次动作在日志与 UI 找到同一请求 ID | 台架所有测试动作 100% 可追溯 | 端到端记录 |
| 限时与停止 | 在规定配置、负载下测 GPIO/水流关闭时间 | 不晚于已声明上限与实测容差；容差先记录再承诺 | 示波/逻辑记录与现场视频 |
| 异常重发 | 断线/超时/重启测试期间自动重复动作次数 | 0 | 请求日志与现场观察 |
| 空状态诚实性 | 未配置、未标定、旧数据是否伪装成实时有效值 | 0 项误标 | 截图矩阵与自动检查 |
| 界面稳定 | 明确版本完整工作日内闪屏、崩溃、触摸丢失 | 先记录实际基线和复现条件 | 帧/串口诊断与人工观察 |
| 维护成本 | 新硬件适配涉及哪些文件、用时和定制行为 | 完成第二种硬件后报告 | 适配 diff 与测试卡 |
| 场景价值 | 使用者愿否继续放桌上，哪些功能被关闭 | 定性原因优先于满意度均分 | 一周后经同意回访 |
| 传播效果 | 点赞/收藏/播放及教程点击，标时间窗与来源 | 先采基线，不预报“爆款” | 平台后台截图与原始计数 |

从一轮小样本得到的问题可以指导改设计，不能直接写“用户效率提升”“焦虑下降”或“市场验证成功”。

## 6. 从单盆到用户自带硬件

### 阶段 A：把一台做实

交付一条可复现的 XIAO + YOYO 链路，保留本地 Indicator 体验。完成安全接线、查询、限时动作、取消/停止、失败与未知。退出条件：新操作者按照教程，在明确条件下复现，并能解释每个结果状态。

### 阶段 B：证明接口能复用

选**第二种真实板卡或第二类单执行器设备**，不要一次宣称覆盖全品类。抽出设备身份、能力描述、传输适配、请求/结果关联和上限策略。区分传感器、执行器、展示设备；没有泵的设备不显示浇水。退出条件：使用同一套契约测试、相同的状态语义和用户确认流程，完成第二条端到端链路。

### 阶段 C：建立可维护的硬件目录

每个硬件条目有型号、修订、电源、电平、固件版本、已验证能力、禁用能力、接线图、适配维护者、测试日期和局限。提供可复现的示例适配器、静态校验和兼容性矩阵。兼容性的单位是“型号 + 固件 + 具体能力”，不是“ESP32 都支持”。详见 [硬件平台方案](device-platform.md)。

设备注册、凭证轮换、撤销、OTA、升级回滚、设备迁移与远程运维均为后续工程，需明确所有权和恢复流程；当前编译期配置不包装成已经存在的 SaaS 管理后台。

### 阶段 D：小范围分区灌溉试验

先选可控的实验区和一种作物/基质，增加合适的流量、水位、阀门/泵状态反馈，验证多区互锁、干转/漏水检测、断网策略、本地时钟与最大日用量。传感器漂移、管路堵塞和现场维护必须进入任务，不只增加“自动浇水”按钮。

给定稳定试验条件后，比较基线与策略的用水量、土壤状态、故障/人工干预、作物指标；注明测量方法、天气/基质和样本差异，再讨论是否节水。没有流量计和对照试验，不报节水百分比。

### 阶段 E：设施农业合作验证

与真实使用者共同定义作物、分区、水肥与维护边界。YOYO 负责解释状态、发起意图和查询记录；本地控制器负责时限、互锁、离线策略和执行。大规模调度不能依赖一段聊天保持在线，也不能把盆栽游戏数值扩写成农艺模型。

退出条件不是“能同时控制更多继电器”，而是现场连续试验、运维恢复、数据质量、角色权限与故障处置均有证据。商业使用与规模化应在这些条件成立后单独决定。

## 7. 证据包怎样保存

建议每次验收建立 `artifacts/acceptance/YYYY-MM-DD/<case-id>/`（目录建议，本文不创建含设备信息的数据），包括：`manifest.json`、匿名日志、接线照片、屏幕/现场录像、结论与未通过项。大体积和私人原始资料留在受控存储，公开仓库只保留脱敏摘要、可授权媒体和必要哈希；不要把 token、SSID 密码、账号或原始私人录音推到 Git。

`manifest.json` 的建议字段包括提交号、固件 SHA-256、Skill SHA-256、硬件修订、操作系统/手机型号、能力开关、测试环境、观察方法、附件哈希和结论。日志时间戳如果来自不同设备，说明时钟源与偏差；优先用请求 ID 关联，不用碰巧相近的墙上时间拼故事。

公开证据页采用“主张 → 方法 → 环境 → 结果 → 限制 → 原始记录入口”的固定格式。更新功能时更新证据日期，不能让新首页继续链接旧镜像结果而不解释。
